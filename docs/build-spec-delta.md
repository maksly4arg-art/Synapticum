## 0. Что такое Delta

- Delta = независимый от Synapticum агент-контур для клиента. Synapticum = штаб/мастерская, Delta = серийное изделие.
- **1 Delta = 1 клиент = свой VPS + своя память/Vault + свой TG-бот + свой веб-UI.** Дельт может быть много: delta-01, delta-02...
- Требование №1 - **реплицируемость**: Delta-02 разворачивается по проторенной дорожке «в 1 клик» (provision-скрипт + .env), а не за 2 недели как первая.
- Связь со штабом: у Builder (Mac) есть ssh/Tailscale-доступ ко всем дельтам - посмотреть, починить, использовать.

## 1. ЗАКОН СБОРКИ - правило фиксации

1. Каждое действие на VPS оставляет след: либо скрипт/конфиг в репо, либо строка в журнале (§7) с ТОЧНОЙ командой.
2. Сделал руками - СРАЗУ конвертируй в скрипт (не «потом»). Руками без следа = запрещено.
3. Цель: к концу сборки Delta-01 существуют `provision.sh` (голый Ubuntu → готовая система) + `.env.example` (все переменные инстанса) + `docs/onboarding.md`. Это и есть «1 клик» для Delta-02.
4. Отличия между дельтами живут ТОЛЬКО в `.env` и Vault-контенте. Код у всех дельт общий (репо `delta`).

## 2. Модель продукта

- **SaaS: VPS всегда наш, НЕ передаётся.** Клиент получает два окна: Telegram-бот (хаб агентов) + веб-UI. Никакого ssh/root/Unix-юзера у клиента.
- Если когда-то продажа С передачей VPS: техподдержка закрывается, наши ключи и подписки убираются (logout = отзыв токена).

### Два тарифа (сосуществуют per-client, выбираются профилем клиента):
- **BYO-подписка** - клиенту принципиальна своя подписка Claude (бюджеты и т.д.). Логин-танец: админ запускает `claude /login` под юзером bob → шлёт клиенту OAuth-URL → клиент авторизуется своим аккаунтом → возвращает код → админ вставляет. Токен клиента на VPS используется ТОЛЬКО для запросов самого клиента (пункт в оферту).
- **Метереный (основной продуктовый)** - движок через API (OpenRouter/Anthropic API, ключ НАШ). У клиента ноль ключей. Каждый вызов пишется в usage-ledger, в веб-UI счётчик остатка + пакеты токенов для пополнения. Баланс <= 0 → вежливый стоп + нотификация админу. Маржа зашита в цену пакета. В пилоте пакет активирует админ вручную после оплаты; платёжный шлюз - потом.

### Граница ToS:
- Подписка персональная: перепродажа ЗАПРЕЩЕНА → подписочный тариф только «клиент принёс свою».
- API создан для перепродажи → метереный тариф строго через API-ключ, НИКОГДА через нашу подписку.
- Админ и клиент могут говорить с одним Bob одновременно - каждый на своей подписке (роутинг §3.4).

## 3. Архитектура инстанса

### 3.1 VPS
- Ubuntu 24.04 LTS, 2 vCPU / 4 GB (минимум 1/2 GB), Vultr (или аналог). Vultr-Santiago <vps-ip> НЕ ТРОГАТЬ - это прод-exit Synapticum.
- Unix-юзеры: `bob` (рантайм: агент под systemd, код, Vault, .env) + `synadmin` (админ, sudo).
- Firewall: наружу только ssh (ключи); весь веб - только на tailscale-интерфейсе.

### 3.2 Bob-lite (агент)
- grammy (TG) + Claude Agent SDK, мышление Topology B: обёртка=дом, движок=слот.
- Чистый порт из ClaudeClaw БЕЗ завязок на Mac. Личность - в системном промпте, не в коде.
- Память: Vault-папка (markdown = граф знаний) + SQLite FTS5 (runtime-кеш/поиск) - зеркало архитектуры Synapticum.

### 3.3 Auth-профили Claude (для BYO и админа)
- `/home/bob/.claude` - профиль клиента (дефолт), `/home/bob/.claude-admin` - профиль админа.
- Выбор через `CLAUDE_CONFIG_DIR` в момент запуска движка. Логин админ-профиля: `CLAUDE_CONFIG_DIR=/home/bob/.claude-admin claude /login`.

### 3.4 Маршрутизация (единый чокпоинт getEngine()/generate())
```
sender_id → профиль клиента (.env / clients-таблица)
  ├─ админ (ADMIN_TG_IDS, веб-чат из tailnet) → SDK, конфиг .claude-admin → подписка админа
  ├─ клиент, тариф BYO                        → SDK, конфиг .claude       → подписка клиента
  └─ клиент, тариф METERED                    → OR/API (наш ключ)         → usage-ledger
```
- Память/Vault ОБЩИЕ для всех собеседников - разделяются только биллинг и сессии.
- generate() в metered-режиме пишет ledger: ts, client, model, tokens_in/out, cost_usd (OR отдаёт цену в ответе).

### 3.5 Веб-UI (два контура, РАЗНЫЕ плоскости доступа - решение юзера 2026-07-24)
- **Принцип: Delta = премиум-продукт БЕЗ СТЫКОВ для клиента.** Клиент НИЧЕГО не устанавливает (Tailscale для клиента отвергнут как «стык» - track-ruled-out).
- **Клиентский UI = ЕДИНЫЙ РАБОЧИЙ ИНТЕРФЕЙС клиента, а не пульт бота (уточнение юзера 2026-07-24).** Второй канал после Telegram: (1) чат с Bob; (2) блок «Процессы» - интеграции: парсинг по API, отчёты (напр. в налоговую), связи с внешними web-ресурсами по http/api; (3) файлы - скачать результат процесса; (4) счётчик остатка + пакеты. Доставка: ПУБЛИЧНЫЙ HTTPS - домен/поддомен на дельту, Caddy (авто-TLS), rate-limit. Вход без пароля: **magic-link из Telegram-бота**. Ноль установок, ноль паролей = премиум-опыт.
- **Админ-панель** (операторская: старт/стоп systemd, живые логи, крутилки, ledger): ТОЛЬКО tailscale0, из интернета не существует. Клиент о ней не знает.
- **Запасной путь поставки: Tailscale = «hardened»-вариант** (уточнение юзера 2026-07-25: не вычеркнут, а в резерве; web - основной). Модель отличий: онбординг дороже (приложение+аккаунт+share-invite на КАЖДОМ устройстве клиента); безопасность выше (443 закрывается совсем, из интернета только ssh; node sharing показывает клиенту одну ноду, ACL до одного порта; шаренные клиенты НЕ тратят лимиты free-плана); риски - конфликт с VPN клиента (bypass 100.64.0.0/10 на каждом устройстве = чиним чужие сети), в РФ координатор Tailscale нестабилен. Нога VPS→Anthropic и весь код НЕ меняются. Ниша: корпоративные/параноидальные клиенты, опция дороже. Гибрид без правок кода: `tailscale serve` → https://delta-01.<tailnet>.ts.net параллельно с web (по команде юзера). ⚠️ tailscale serve: Enable нажат юзером 2026-07-25, РАБОТАЕТ: `tailscale serve --bg 8080` → **https://delta-01.tail4bdaee.ts.net** (tailnet-only, proxy на 127.0.0.1:8080 = кабинет; выключение: `tailscale serve --https=443 off`). Тест с Mac: raw 200 «Delta · вход»; через прокси-порт Clash ts.net НЕ резолвится (exit 35) - браузеры в TUN-режиме ходят системным резолвером (Tailscale ставит scoped-resolver на ts.net), Chrome под вопросом, Safari эталон. Оба входа живут параллельно: публичный Caddy (клиенты) + ts.net (hardened/админ). Chrome под Clash TUN: ERR_CONNECTION_CLOSED - fake-ip хайджекит DNS ts.net (Chrome-резолвер ≠ системный scoped-resolver). ФИКС без трогания Clash: `echo "100.94.142.99 delta-01.tail4bdaee.ts.net" | sudo tee -a /etc/hosts` + открывать строго https:// (serve не слушает 80). Системная альтернатива: `*.ts.net` в fake-ip-filter Clash Verge. Это живое подтверждение модели «hardened-стык»: клиентам с VPN/fake-ip DNS нужна строка hosts/правило - публичная линия таких приключений не имеет.
- **2026-07-25** - EXIT NODE протестирован, вариант РАБОЧИЙ (вердикт юзера). VPS delta-01 объявлен exit node (advertise 0.0.0.0/0+::/0, IP-форвардинг, одобрен в консоли). Механика по трассировке route -n get: Clash ВКЛ → обычный трафик (1.1.1.1) и внешние WG-пакеты Tailscale идут через utun1024 (Clash TUN) → всё внутри Clash-туннеля, exit node для общего трафика спит; Clash ВЫКЛ → всё через exit node (VPS NL). ⚠️ НЮАНС: в связке Clash-TUN + Tailscale **Web UI по tailnet НЕ открывался без exit node** - включение exit node побочно чинит роутинг (поднимает direct-линк к real-IP VPS). Механизм «нечаянный», возможна хрупкость; чистые альтернативы (SSH-форвард, публичный web) надёжнее. Отмена exit node - кнопкой в приложении (Exit Node→None), не командой.
- **2026-07-25** - ОПЕРАТОРСКАЯ СУПЕРСИЛА (в архитектуру): каждый Delta-VPS добавляется в tailnet АДМИНА → переключением exit node админ «встаёт» на сеть любого клиента (delta-01/02/03...) и видит интернет их сервера - воспроизведение жалоб «нет связи», диагностика с их egress. Клиенты при этом НЕ в tailnet админа (у них web).
- **2026-07-25** - ТРИ ДВЕРИ ПОСТАВКИ (финальная модель после тестов): (1) **Web/Caddy** - простой безотказный путь, дефолт, «клиент хочет скидку»/не настраиваем связь; (2) **Tailnet** - hardened для дружественных сетей (не-DPI); (3) **Exit node** - операторский доступ админа + режим «весь трафик клиента через его VPS». Для DPI-стран ни web-Caddy, ни tailnet голым не идеальны → потенциальный 4-й «stealth»-профиль: Reality-фронт (Xray VLESS+Reality) снаружи, mesh/WG внутрь (nesting; Reality нельзя нативно на WG - нужен VLESS-носитель). Tailscale-клиенты: macOS/Windows/iOS/Android/Linux - все платформы.

### 3.6 Сеть
- Tailscale = ТОЛЬКО админ-плоскость (VPS + Mac админа). Одноразовая настройка админа; клиенты не в tailnet никогда. Free-план: 3 юзера / 100 устройств - хватает.
- ufw: наружу ssh + 443 (Caddy, появится на шаге веб-UI); админ-порты только tailscale0.
- Понадобится домен для клиентского UI (поддомен на дельту, напр. delta01.<домен>) - вопрос к юзеру на шаге 7.
