# Build-spec: тяжёлая LLM на Mac Studio (96 ГБ)

## ЦЕЛЬ
Юзер ставит локальную LLM с требованием **80-85 ГБ RAM** и хочет, чтобы она
надёжно влезала и работала на Mac Studio (96 ГБ unified memory). Рантайм -
**Ollama** (стоит: `~/.local/bin/ollama`). Возможны LM Studio / llama.cpp / MLX.

## ГЛАВНЫЙ ВЫВОД (то, ради чего весь разбор)
Узкое место - **НЕ «лишние процессы», а скрытый лимит видеопамяти macOS**.

- На Apple Silicon память общая (CPU+GPU). По умолчанию macOS отдаёт под GPU/модель
  только ~70% RAM.
- Проверено: `sysctl iogpu.wired_limit_mb` = **0** (дефолт) → потолок ~67 ГБ.
- **Модель 85 ГБ БЕЗ поднятия лимита не загрузится на GPU**, сколько процессов ни убивай.
- Решение: `sudo sysctl -w iogpu.wired_limit_mb=92160` (90 ГБ, оставляем ~6 ГБ системе).
  Это потолок-РАЗРЕШЕНИЕ, не резервирование. Сбрасывается при перезагрузке.

Убийство фоновых процессов даёт всего +3-5 ГБ - это вторично.

## ГОТОВЫЙ ИНСТРУМЕНТ
Скрипт-подготовка (запускать ПЕРЕД стартом модели):
```
bash ~/Synapticum/free-ram-for-llm.sh        # лимит 90 ГБ по умолчанию
bash ~/Synapticum/free-ram-for-llm.sh 88      # свой лимит в ГБ
```
Файл: `/Users/synapticum/Synapticum/free-ram-for-llm.sh`
Делает: поднимает iogpu.wired_limit_mb → закрывает Chrome/Preview/Activity Monitor →
`sudo purge` → печатает RAM до/после → напоминает ручные шаги. Боты и прокси НЕ трогает
намеренно (чтобы не убить сессию/туннель).

## РЕАЛЬНАЯ ПРИКИДКА «ВЛЕЗЕТ ЛИ 85 ГБ»
```
96 ГБ всего
-85 модель
- 9 пол macOS (wired ~5 + графика WindowServer ~1.4 + демоны)
= ~2 ГБ запаса  → НА ГРАНИ
```
85 ГБ запустится, но с нулевым запасом: риск фриза или ухода модели в swap (инференс
падает до неюзабельного). **РЕКОМЕНДАЦИЯ: целиться в модель ≤78 ГБ** (квант Q4-Q5 вместо
Q6-Q8) - будет работать с запасом. 85 ГБ только если всё закрыто и ничего не открывать в сеансе.

## ФАКТЫ ПРО ПАМЯТЬ MAC (чтобы в новой сессии не пересчитывать с нуля)
- Всего 96 ГБ. Wired (несжимаемый пол ядра) ~5 ГБ. WindowServer ~1.4 ГБ (графика, цена
  большого Dell-монитора). Это пол, не режется.
- **RSS врёт**: сумма RSS по процессам (~19-29 ГБ) включает общие системные библиотеки,
  посчитанные у КАЖДОГО процесса. Реальная App-память (anonymous pages из vm_stat) ~12 ГБ.
  Для правды по процессу - top MEM (footprint), не RSS.
- Из ~723 процессов **683 (94%) - Apple core (сам macOS), неубираемо**. Только ~32 - своё.
- «Cached Files» в Activity Monitor - НЕ занятая память, отдаётся мгновенно (free RAM = wasted RAM).
- **RAM-оптимизаторы (CleanMyMac Memory и пр.) - развод и вредны**: дёргают `purge`, кэш
  перечитывается с диска = медленнее. Не ставить. Единственная легит-оптимизация =
  убрать своё из Объектов входа.

## ОТКРЫТЫЕ ВОПРОСЫ
- Точная модель и квант (блокер для финального вердикта по 85 ГБ).
- MoE или dense? (MoE держит в памяти только активных экспертов - может вести себя легче).
- Нужен ли длинный контекст (KV-кэш добавляет ГБ сверх весов).

## ЗАМЕРЕНО НА ПРАКТИКЕ 2026-06-17 (qwen3.5:122b = Finn Senior)
Прямые тесты на работающем Ollama (iogpu.wired_limit_mb=92160 / 90 ГБ), модель `qwen3.5:122b` (125B MoE, **Q4_K_M**, family qwen35moe, 48 слоёв):
- **Веса: 80.7 ГБ** (size_vram при num_ctx=4096). Это база, дальше только KV.
- **KV-кэш ОЧЕНЬ дешёвый (GQA):** num_ctx 4k → 80.7 ГБ; 32k → 81.4 ГБ (+0.7); 140k → 84.1 ГБ (+3.4). То есть **~0.024 ГБ на 1k токенов**. Память - НЕ узкое место для контекста (вопреки первой прикидке: я ошибочно решил, что 50k не влезет - юзер был прав, что надо мерить).
- **Тесты needle+reasoning (досье с 270/980 проектами-дистракторами, факты разбросаны):**
  - 28k контекста: total ~2 мин (чтение 24.4k @ 455 tok/s = 54с + генерация 41 tok/s). Пик RAM 95G, **swap плоский** (не рос). Качество: 4/4 факта + риск-вывод верно.
  - **103k контекста (реальный токенайзер; ~122k по символам): total ~10 мин** (load 22с + чтение 103430 tok @ **266 tok/s** = 388с + генерация **25.7 tok/s** = 186с). Пик RAM 95G, **swap плоский 450M все 400с - ноль тресхинга, ноль фриза.** Качество: 4/4 факта + риск-вывод верно на всю длину.
- **ВЫВОД:** на 96 ГБ qwen3.5:122b держит **100k+ контекста по памяти спокойно** (RAM не лимит). Реальный лимит = **СКОРОСТЬ ЧТЕНИЯ промпта**, падает с длиной (455→266 tok/s от 28k к 103k); 100k ≈ ~10 мин на запрос. Для частого большого контекста где важна скорость - Middle/Scout быстрее; Senior = глубокое рассуждение, готов ждать. Фриза, которого боялись для 80-85 ГБ моделей, НЕ случилось - swap оставался плоским даже на пике 95G/96G.
- РЕШЕНО 2026-06-18: num_ctx прописан **per-model** в OpenClaw (`models.providers.ollama.models[].params.num_ctx`), тир-зависимо по RAM:
  - **Junior `qwen3.6:27b-q8_0` = 262144 (256k)** — нативный максимум модели (33GB веса + ~26GB KV ≈ 59GB, влезает с запасом).
  - **Middle `llama4:scout` = 524288 (512k)** — практический RAM-max (нативно 10M, но это RAM-невозможно). Scout = контекст-машина, KV дешёвый (size_vram остался 67.1GB даже на 512k). На 512k загрузился и ответил; swap подрос ~5GB ТОЛЬКО из-за общей загрузки (67GB модель + открытые приложения + Claude-desktop-сессия ~27GB база), не из-за KV. Для самого тяжёлого 512k-юзинга — освободить RAM (RAM-тоггл / закрыть приложения).
  - **Senior `qwen3.5:122b` = 131072 (128k)** — КАПНУТ по RAM (80.7GB веса оставляют ~6GB под KV; 128k=83.9GB, выше упирается в потолок).
  - Проверено через gateway (`openclaw agent --agent finn`): size_vram прыгнул до 83.9GB на Senior → num_ctx РЕАЛЬНО доходит до Ollama через нативный адаптер; Finn в Telegram берёт большой контекст без обрезки. Менять = `openclaw config patch` массива models (lossless replace) + kickstart. Глобальный `OLLAMA_CONTEXT_LENGTH` не понадобился.
