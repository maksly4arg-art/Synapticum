# Канон для агентов Synapticum

Канонический чеклист + принципы. Любой новый агент собирается по этому документу.
**Две задачи Канона:**
1. **Скорость + качество создания** — развернуть агента за ~полчаса (собрал по Канону, повесил
   скиллы, сразу качаешь узкие навыки/схемы, а не настраиваешь память/движок/синтаксис заново).
2. **Функциональная устойчивость в работе** — повторяющиеся критичные баги чиним ОДИН раз и
   канонизируем командой **«обнови Канон»** (§0.2): дальше каждый новый агент рождается уже без них.

Эталоны кода: `Analyst/src/` (память/движок), `Bob/src/` (гибрид-память + /handoff),
`Eva/src/publisher.ts` → `Shared/tg-format` (Telegram-синтаксис).

> **История:** §3/§3.1 (память) и §4 (A2A) были переписаны 2026-06-21 — старый закон
> «память только в общем Archivarius, НИКОГДА resume» заменён на реально построенную
> модель (своя `<agent>.db` + нативный resume + catch-up). Это явное противоречие,
> разрешено по решению владельца. Остальное дополнено, не удалено.

## 0. Главный принцип: дом + сменный движок

Агент = **наша обёртка** (наш TS-код), которая владеет ЛИЧНОСТЬЮ. Под ней — **сменный
движок** (мозг). Обёртка держит: Telegram, идентичность/инструкции, ПАМЯТЬ, A2A,
спец-поведение. Движок только думает.

```
   НАША ОБЁРТКА (дом)  =  Telegram + личность + СВОЯ память (.db) + A2A
            │ engine.ts: getEngine() выбирает слот
     ┌──────┴───────┐
 BuilderMode      ORmode
 Claude Agent SDK  OpenClaw → OpenRouter (реальные тулы/веб)
 (Claude-модели)   (любые модели, DeepSeek v4 pro = база)
```

**Смена движка ≠ новый агент.** Память и личность общие, в обёртке. Движок меняется
тоглом в лаунчере, агент остаётся собой.

### Две топологии — по ПЕРВИЧНОСТИ (что «дом», что «резерв»)

И обёртка-grammy, и OpenClaw умеют быть фронтом агента. Решает, что у агента ПЕРВИЧНО
(как он создан):

- **Первичен Claude + grammy** (Bob, Alice, Jesse, Eva, Joe, Aleks, Freddy): дом = наша
  обёртка (grammy Telegram + личность + наша `.db`-память). OpenClaw — ВТОРОЙ, дублирующий
  путь: резервный движок-слот (ORmode), включается тоглом. Telegram живёт в обёртке.
- **Первичен OpenClaw** (Finn): фронт = НАТИВНЫЙ OpenClaw — нативный Telegram-канал (БЕЗ
  grammy) + нативные тулы (`canvas`, `browser`, `file-transfer`, hands-MCP…). Но память и
  рабочее место — НАШИ: своя `.db` (finn.db) + наша личность/правила (`rules/finn.md`), а
  НЕ движок-нативная память (OpenClaw memory-core).

**Инвариант обеих топологий: память ВСЕГДА наша** (своя `.db`, не память движка). Разница
только во фронте/рантайме-первичности. Первичность фиксируется при рождении агента (см. §12).

## 0.1 Протокол сборки «сделай агента по Канону»

Когда владелец говорит «сделай такого-то агента по Канону», Билдер:
- **Где характеристики у всех ОДИНАКОВЫ и сходятся** (см. таблицу §12 — столбцы без расхождений)
  → делает ТАК ЖЕ ПО УМОЛЧАНИЮ, не спрашивая (движок-тоггл, своя .db, resume/инжект,
  catch-up, FTS, /handoff, A2A-порт, typing, tg-format-синтаксис, voice, vault-env, скелет).
- **Где характеристики РАСХОДЯТСЯ между агентами** (роль, OR_MODEL-дефолт, окно памяти,
  resume vs чистый инжект, источник FTS, нужен ли vision/руки, своя ли личность-память,
  свой ли Telegram-синтаксис) → **задаёт владельцу вопрос, что ставить.**
- Узкие навыки/скиллы/схемы вешает владелец сам сверху — Канон даёт каркас, не предметку.

## 0.2 Команда «обнови Канон» (принцип: fix once → capture → apply everywhere)

Это вторая задача Канона (§задача 2 выше). Когда у агентов В РАБОТЕ всплывает баг — чиним.
Если баг **повторяющийся** (один КЛАСС, всплывает в разных местах/у разных агентов) и
**критичный** — не патчим N раз одно и то же, а чиним ОДИН раз и канонизируем.

**Триггер — владелец говорит «обнови Канон».** По этой команде Билдер:
1. **Выделяет КЛАСС бага + корень** (а не точечный симптом конкретного агента).
2. **Записывает канонический фикс** в профильный раздел Канона + строку в реестр ниже.
3. **Делает фикс ДЕФОЛТОМ** для всех текущих и будущих агентов — врезает в протокол сборки §0.1,
   чеклист §13 и (где уместно) таблицу §12. Чтобы это НИКОГДА не дебажилось по-агентно заново.
4. **Раскатывает на текущий флот** и фиксирует статус (кто получил, кому осталось, исключения).

Смысл: повторяющийся критичный баг = ОДНА запись в Каноне, а не N одинаковых патчей. Один раз
поняли корень → дальше новый агент рождается уже с фиксом, старые подтянуты разом.

## 0.3 Секреты и токены — единый ВИДИМЫЙ дом

Любой кред агента (Telegram bot token, API-ключи) живёт в центральном свитчборде
`Vault/_config/<agent>.env` — это ЕДИНЫЙ видимый источник, который читает обёртка
(`readEnvFile`). Правило (корень — кейс Finn 2026-06-22):

- Владелец выдал токен → Билдер **СРАЗУ** пишет его в `Vault/_config/<agent>.env`
  (+ строка в реестр токенов ниже). НЕ только в рантайм-конфиг.
- Рантайм (OpenClaw gateway, `~/.openclaw/openclaw.json` → `channels.telegram`) может
  держать СВОЮ копию — но она НЕ заменяет видимый дом. Кред, лежащий ТОЛЬКО в
  `~/.openclaw/` или ином скрытом месте = «потерян»: был кейс — токен Finn жил в
  OpenClaw-конфиге, поиск по `.env`/проекту его не нашёл → владелец выдавал второй раз.
- При «не могу найти токен» — проверять и `~/.openclaw/openclaw.json` (channels), и
  HOME, прежде чем просить владельца выдать заново.

## 0.4 Контур OpenClaw: Билдер ЗНАЕТ состояние и ищет инструменты ТАМ

Два правила про работу Билдера в контуре OpenClaw (корень — кейс 2026-06-22: токен
«потерян» + презентации полезли через Claude-инструмент мимо нативного OpenClaw).

**1. Билдер ОБЯЗАН знать состояние OpenClaw — не «делать вид, что не знает».**
`~/.openclaw/openclaw.json` — известное место. Перед работой с OpenClaw-агентом СНАЧАЛА
читай его: `agents.list[]` (id, `tools.profile`, model), `channels` (токены!), `plugins`,
`mcp.servers`, `bindings`, gateway-лог `~/Library/Logs/openclaw/gateway.log`. Если «мы это
уже делали» — значит оно ТАМ уже есть: читай, а не спрашивай владельца заново. (Связка с §0.3.)

**2. В контуре OpenClaw инструменты задачи ищем В OpenClaw — ПО УМОЛЧАНИЮ, ПЕРВЫМИ.**
Билдер знает Claude/SDK-тулы «из коробки» и тянет их рефлекторно — ЗАПРЕЩЕНО хватать
знакомый Claude-инструмент и переписывать под него весь контур. Сначала ищем нативное:
- `openclaw docs <запрос>` — штатный поиск по живым докам OpenClaw;
- `openclaw plugins list` + загруженные плагины (canvas, browser, file-transfer…);
- профиль тулов агента (`tools.profile: "full"` = все нативные тулы) и `mcp.servers` (свои MCP).

**Пример (на котором и поймали):** презентации.
- OpenClaw-первичный агент (Finn) → нативный тул **`canvas`** (model tool-use): отдаёт
  gateway viewer-URL + готовый PNG/PDF в Telegram. `pptxgenjs` здесь ЛИШНИЙ.
- Claude+grammy-агент → `Shared/report-engine` (`generatePresentation`, pptxgenjs) — это
  ИХ контур.
Один класс задачи, две реализации — по первичности агента (§топологии в §0).

## 1. НИКАКИХ РЕШЕНИЙ ПО УМОЛЧАНИЮ (закон)

- **Явный тоггл, а не угадывание.** Режим движка = `<AGENT>_MODE` в env, читается явно
  (`getEngine()`), не «есть ли ключ».
- **Без тихого кросс-фолбэка.** ORmode упал → ошибка пользователю, агент НЕ отвечает молча
  через Claude. И наоборот. (`runViaOR` возвращает `text:null`+error, обёртка показывает ошибку.)
- **Агент > скрипт (арх. закон).** Где хардкод-скрипт перебивает/подменяет суждение агента —
  УБИРАТЬ, не сужать. Анти-паттерны: keyword-гард по триггер-слову; re-prompt-петли,
  переписывающие намерение; **gating ответа за `if(reply)`** (ход пуст → ТИШИНА — кейс «Ева
  замолчала»); keyword-роутеры мимо мозга. Ответ/прогресс ДОЛЖЕН доходить ВСЕГДА (пусто →
  fallback-текст). Чистые UI-кнопки (✅/❌) — ок. См. [[feedback_agent_over_script]].
- **Граница «агент > скрипт»: полномочия - в КОДЕ (закон, 2026-07-07).** Агент судит и учится сам -
  поведение/стиль/решения НЕ хардкодить (пункт выше, сознательный выбор владельца). Но **полномочия,
  безопасность и деньги** - кто вправе дать работу, супервизор-цепочка, бюджет-лимиты, авто-старт,
  разрушающие действия - это НЕ суждение, это контракт: гард в коде обёртки на ВСЕ work-inducing
  входы (не на один тип), промпт лишь дублирует смысл. Тест: переключи агента на самый дешёвый мозг -
  если инвариант можно уговорить или забыть, ему место в коде. (Кейс: «Aleks NEVER стартует сам» жил
  только текстом - `task_request` принимался от любого агента.)
- **Промпт не описывает несуществующие механики.** Каждая механика в промпте (уровни, авто-рефлексия,
  счётчики прогресса) обязана иметь опору в коде/БД (таблица, хендлер, инкремент). Описал - собери
  или вырежи: мёртвая инструкция жгёт токены и учит агента фантазировать о собственном устройстве.
- **Один источник правды на состояние.** Два хранилища одного состояния ДРЕЙФУЮТ (агент читает
  одно, код/кнопки пишут в другое → повторы/призраки). ОДИН источник, агент читает его, код пишет
  В НЕГО ЖЕ. Метку «где мы / что дальше» ВЫЧИСЛЯТЬ из состояния, не вести вторым полем (протухнет).
- **Без фейк-контролов.** UI без рабочего бэкенда не вешать: провести бэкенд или не показывать.
  Честное «пока нет» > кнопка-обманка.
- **Fail loud.** Молчаливая деградация хуже явной ошибки.

## 2. Движок: параллельная схема OpenClaw + SDK (Topology B)

Один чокпоинт `<Agent>/src/engine.ts`:
- `getEngine()` — читает `<AGENT>_MODE` из `Vault/_config/engines.env` (`openrouter` | `builder`).
- `generate(...)` — единственная точка вызова модели:
  - `builder` → локальный `agent.ts:runAgent()` = Claude Agent SDK `query()` (тулы/веб у SDK встроены).
  - `openrouter` → `Shared/agent-engine` `runViaOR()` → `runViaOpenclaw()` = `openclaw agent --json`
    (реальные тулы/веб через OpenClaw).
- ВСЕ места вызова модели идут ТОЛЬКО через `generate()`. Прямых `query()`/`runLLM()` в хендлерах нет.

Транспорт ORmode живёт в shared-модуле `Shared/agent-engine/` (один на флот): `runViaOR()`
диспетчит solo (через OpenClaw) и fusion (HTTP-плагин); `runViaOpenclaw()` спавнит
`openclaw agent`, парсит `.result.payloads[0].text` (поле `.status` на ВЕРХНЕМ уровне).
Реестр моделей — `Shared/agent-engine/index.js:MODELS`/`OR_MODES`.

Провайдинг — два пути синтезированы под одним `generate()`:
- **Claude Agent SDK** (builder): подписка, нативные тулы/вижн, своя сессия (`--resume`).
- **OpenClaw → OpenRouter** (ORmode): нейтральный рантайм, любые модели, реальный agent-loop,
  своя сессия (`--session-key`). OpenClaw-агент регистрируется в `~/.openclaw/openclaw.json:agents.list`
  с НЕЙТРАЛИЗОВАННЫМ workspace (6 comment-only `.md`: IDENTITY/SOUL/AGENTS/TOOLS/USER/HEARTBEAT —
  личность несёт НАШ промпт, иначе двойная персона + лишние токены).

Подключение модуля (как все Shared): в `package.json` `"agent-engine": "file:../Shared/agent-engine"`,
симлинк в `node_modules`, импорт `from 'agent-engine'`. Shared — ESM `index.js`+`index.d.ts`, без build-шага.

## 3. Память: своя `.db` у каждого, движок-агностик (КАНОН 2026-06-21)

> Заменяет старый «общий Archivarius / никогда resume». Реальная модель: **у каждого
> агента СВОЯ `<agent>.db`, контексты не смешиваются**, и память **движок-агностик** —
> переживает переключение Claude↔OR в ОБЕ стороны.

**Где живёт.** Своя `<agent>.db` (sqlite, `<Agent>/store/`) — это весь локальный СКЛАД
агента, не только диалог:
- `conversations` (+ `conversations_fts`) — сырой лог реплик (`chat_id, role, content, created_at|timestamp`).
- `sessions` — указатель `chat_id → Claude sessionId` (НЕ сам диалог).
- `engine_runs(chat_id, engine, last_ts)` — когда каждый движок последний раз отвечал (для catch-up).
- `memories` (+ `memories_fts`) — **второй слой, только у Bob/Eva**: дистиллят (semantic/episodic
  + salience + decay; наполняется `insertMemory`, regex-классификация, БЕЗ LLM-саммари).
- доменные таблицы (trades, journal, lessons-fts, tasks…) — предметка агента.

**Закон уникальности:** `archivarius.db` — НЕ для диалога флота. Каждый агент пишет/читает
СВОЙ `<agent>.db`. (Freddy мигрирован с archivarius.db на `freddy.db` 2026-06-21.)

**Двухслойная память + FTS-поиск:**
1. **Уроки/знание (long-term):** `vault-lessons` `buildVaultContext` инжектит уроки из Vault;
   `[[SAVE_LESSON]]`-маркеры пишут новые.
2. **Диалог (short-term):** `conversations` своей `.db`. В промпт идёт **окно** (последние N) +
   **FTS-топ-K** по ключевым из текущего сообщения (вытаскивает старое за пределами окна).
   Источник FTS: сырые `conversations` (Jesse/Alice/Aleks/Joe/Finn) или дистиллят `memories`
   (Bob/Eva). По токенам они ≈ равны (memories НЕ суммаризирует — сырьё с капом); рычаг
   экономии = размер ОКНА + K, не выбор таблицы.

**Что видит модель ≠ весь склад.** `.db` растёт безгранично (append), но **читается выборочно**
(`LIMIT N` + FTS-топ) → растёт только диск, не промпт/цена. Архив не ротируем под окно
(иначе теряем FTS-поиск по старому); при нужде — архивируем старые строки, не удаляем.

## 3.1 Resume / Inject / Catch-up: движок-агностик в обе стороны

Память «общая» = живёт в `.db` (пишется в ЛЮБОМ режиме). Различается ДОСТАВКА в модель:

- **Resume** = движок сам открывает СВОЮ приватную стенограмму и продолжает. Дёшево
  (prompt-cache), полно, держит tool-state. Но **движок-приватно**: Claude `sessionId` ≠
  OpenClaw `session-key`, форматы несовместимы, через стык НЕ переносится.
- **Inject** = мы руками вклеиваем ходы из `.db` текстом в промпт. Работает на ЛЮБОМ движке.

**Гибрид (resume-класс агентов):** каждый движок использует СВОЙ нативный resume
(Claude `sessionId`; OR `sessionKey=agent:<id>:<chatId>` через `runViaOR`), а стык Claude↔OR
мостит **catch-up из `.db`**:
```
engineKind = getEngine();  lastTs = getLastRun(chatId, engineKind)
recall = lastTs==null ? seed(окно N)               // первый заход движка в чат
                      : catchup(getConversationsSince(chatId, lastTs, 10))  // только пробел от другого движка
prompt = identity + operating-modes + lessons + FTS-топ + recall + message
// Claude: resume(sessionId);  OR: sessionKey=agent:<id>:<chatId>
после ответа: setLastRun(chatId, engineKind, now)
```
Подряд тот же движок → catch-up ПУСТ (resume несёт). После переключения → catch-up = ровно
ходы другого движка → один раз подкинули, дальше снова нативный resume. **Симметрично в обе
стороны** (каждый движок инжектит «что было, пока Я не отвечал»).

**Гоча `session_id` (канон-фикс 2026-07-03, реестр §0.2):** SDK отдаёт id сессии в
init-событии как snake_case **`session_id`**, НЕ camelCase `sessionId`. Читать
`const sid = evt.session_id ?? evt.sessionId`. При нарушении resume мёртв ТИХО: агент отвечает
(на догоне/инструкциях), но каждый ход — свежий контекст. Боевой кейс Евы: без памяти хода
голая строка «▌КОНТЕНТ-ЗАВОД. TELEGRAM» прочитана как «заголовок → делай пост» → юзеру
вывалился пост из доски вместо конвертации шрифта.

**Чистый инжект (Joe/Freddy):** без resume/engine_runs/catch-up — ВСЕГДА инжектят окно N из
`.db` на обоих движках. Симметрично by construction. Дешевле кодом, дороже токенами (нет кеша).

**Окна (живые):** Jesse/Alice/Eva/Aleks 30 · Finn 50 · Bob 20 · Joe/Freddy 10 · catch-up кэп 10.
Кап длины хода ~1500 симв.

**Три бага при нарушении (диагностика):** split-brain (стор не общий) · зависимость от
session-resume (переключился — контекст рвётся) · дыры записи (ветка забыла `saveConversation`).

**Тай-брейк при чтении (важно):** user+assistant одного обмена часто пишутся в ОДНУ секунду →
`ORDER BY <time> DESC` без тай-брейка путает их местами (ответ раньше вопроса). Всегда
`ORDER BY <time> DESC, id DESC` (затем reverse в хронологию). Тот же риск в любом чтении по времени.

**Действия вне диалога → В КОНТЕКСТ.** Кнопка/код, меняющий состояние (approve/reject), но НЕ
доносящий решение в контекст агента → агент его не видит → повторяет/противоречит (кейс: reject
менял БД, но агент на «следующий» делал ту же тему). Фикс: после out-of-band действия — записать
его ходом в `.db` (попадёт в catch-up/инжект) ИЛИ инжектнуть решение в контекст. Доносить РЕШЕНИЕ
в мозг, а не только мутировать БД.

## 3.2 /handoff — «готовься к переключению»

Перед сменой движка посреди ДЛИННОЙ задачи (где catch-up=10 не покроет весь пробел и теряется
tool-state) владелец даёт `/handoff` (или фразу «готовься к переключению»): агент пишет
КОМПАКТНУЮ сводку состояния (над чем работаем, решения, следующий шаг) → она ложится ходом в
`.db` → catch-up подхватывает её на другом движке. У A2A-воркеров без юзер-чата (Finn) — нет.

## 3.3 Самознание агента (блок `[Operating modes]`, оба движка, всегда)

Инжектится в промпт КАЖДЫЙ ход (а не только в инструкциях), чтобы агент знал устройство:
> «Ты можешь работать на Claude или дешёвом OR-мозге (DeepSeek/Kimi/…) — переключает владелец
> под задачу. Твоя память = блоки контекста ([Recent], [Догон], [Restored memory],
> [Self-learning], [Instructions], [Location]) — это факты, опирайся на них. НИКОГДА не говори
> «памяти нет / сессия пустая / индекс сломан» (анти-конфабуляция). `/handoff` = пиши сводку
> состояния, она переживёт смену движка. Смена движка ≠ смена тебя.»

## 4. Связь между агентами: A2A (синхронный HTTP, КАНОН 2026-06-21)

> Решение владельца: **ОДИН протокол — синхронный HTTP** (и локально, и для будущих серверных
> агентов). НЕ строить таблицы-очереди/polling: «агент не полезет / полезет не вовремя → цепь
> ляжет». Синхронный результат предпочтителен.

Модуль `a2a-server` (Shared). HTTP JSON-RPC 2.0 на localhost, порт на агента:
```
eva:41001 alice:41002 bob:41003 jesse:41004 joe:41005 freddy:41006 aleks:41007 finn:41008
```
- Старт: `startA2AServer({ agentId, name, port, asyncMode:true, onMessage })`.
- Отправка: `sendA2AMessage(from, to, type, payload, inReplyTo?)` → POST на `127.0.0.1:<порт>`.
- Приём: `onMessage(fromAgent, type, payload, taskId, inReplyTo, messageId)` — диспетч по `type`.

**Отказоустойчивость при СМЕНЕ РЕЖИМА** (смена движка = рестарт процесса ~секунды):
- **Отправитель ретраит** (`sendA2AMessage`, бэкофф 1/2/4/8/16с ≈ 31с) — дозванивается, когда
  цель поднялась. (Ретраятся connection-fail + 5xx; 4xx и RPC-ошибки — нет.)
- **Приёмник самозаживляет порт** (`a2a-server` ретраит `listen` при `EADDRINUSE`) — иначе при
  занятом порте в момент рестарта агент глух и цепь рвётся.
- Цепь re-исполняется с упавшего узла (синхронная семантика; владелец это принял — «с постами
  работает»). Идемпотентность НЕ обязательна (отвергнута сложность очереди); где побочки
  опасны при повторе — гард точечно у агента.

**Гоча:** чтобы агент ПОЛУЧАЛ результат (напр. `finn_result`), его `onMessage` ДОЛЖЕН принимать
этот `type`. Забыл — ответ молча теряется. Новый тип = добавить и отправку, и handler.

**Рудимент УБРАН (КАНОН 2026-06-29):** легаси SQLite-шина `agent_messages` (write+poll,
`startInteragentPoller`, `waitForResponse`, `observe*`, `pollFreddy*`) ВЫПИЛЕНА у всех 8 агентов —
она нарушала это правило (очередь+polling) и роняла обмен: ответ requester'у, у которого НЕТ
своего A2A-сервера, улетал в закрытый порт. Следствие правила: **requester ОБЯЗАН поднимать свой
`startA2AServer` и иметь `onMessage`-case на КАЖДЫЙ ожидаемый ответ** — результат приходит PUSH'ем
в его `onMessage`, НЕ поллингом БД. Архивариус остаётся ТОЛЬКО как кеш/FTS/поиск/реестр, НЕ канал
связи — и в архитектурных решениях про связь агентов он больше не упоминается. Вне A2A осознанно:
`builder_tasks` (мост агент→Билдер/Claude-Code, не A2A-узел).

### 7.1 Синтаксис сообщений (КАНОН — `Shared/tg-format`)

## 10. Лаунчер: режимы и как они работают

Лаунчер `ClaudeClaw/launcher.pyw` (tkinter, единственный) — карточка на агента.

**Панель движка (под карточкой), два ряда:**
- **Ряд Claude:** `[Claude]` + модели `[Opus 4.8][Sonnet]` (+ у Bob кнопка `[Builder]` — мост be-bob).
  Выбор → `<AGENT>_MODE=builder` + `CLAUDE_MODEL`.
- **Ряд OR:** `[OR]` + мозги `[DS][Kimi][Gem][Fus][Max]` → `<AGENT>_MODE=openrouter` + `<AGENT>_OR_MODEL`.
- Светится только активный ряд. Тоггл пишет в `engines.env`; **смена режима = рестарт карточки**
  (config кешит env на импорте). $-счётчик на карточке красится по активному мозгу.

**«Builder»-мост (только Bob):** кнопка-ДЕЙСТВИЕ — гасит grammy-агента и оборачивает ЖИВУЮ
Claude-сессию в Telegram Боба через `bob-telegram` MCP (`be-bob.py`). Это РЕЖИМ, не часть
обычного движка; обычно выключен. Карточка Bob это сохраняет.
- **Паттерн «гейткипер» (дешёвый автономный inbound):** опрос — НЕ-LLM циклом (curl getUpdates
  long-poll ~50с, **$0 в простое**); LLM (`claude -p`) дёргать ТОЛЬКО когда реально пришло сообщение.
  Не гонять модель на пустых опросах. (Так устроен be-bob.)

**Счётчик денег по движкам:** агент логирует ТОЛЬКО токены (`model='or:<MODE>/<KIND>'` — MODE =
выбранный движок для атрибуции, KIND = реально сработавшая модель для цены; vision слепого мозга →
KIND=`gemini`). **Формула цены — в лаунчере** (токены × редактируемый множитель из источника, не
«из головы» [[stale_data_rule]]), не в агенте. **Генерация картинок** (Flux/fal.ai/Gemini-image) =
отдельный биллинг провайдера, в токен-счётчик НЕ писать.

**Рубильник процессов (точки опоры):** любой стоп/старт/рестарт карточки → точечный kill ВСЕХ
процессов агента по **dist-пути** (не по голому имени — иначе матчит дев-сессии) + хелперы
(`be-bob.py`). Крестик / dock-Quit / Cmd-Q = полное выключение + kill всех агентов. НИКОГДА не
blanket-kill `claude` (убьёт интерактивные сессии). Кнопки `Restart All`/`Stop All`.
- **Tk НЕ потокобезопасен.** Воркер-тред (health/usage), трогающий `self.after()`/виджеты из
  НЕ-главного потока → SIGSEGV (краш каждые 2-3 мин; диагноз `Tcl_AfterObjCmd` в python crash-логе).
  Воркеры кладут результат в `queue.Queue`, главный поток разгребает `self.after(200, pump)` и ТОЛЬКО
  там трогает Tk. Любая новая карточка с фоновым опросом — по этому правилу.

## 11. Сводка гоч (на чём обожглись)

- **dist-дрейф:** правка без пересборки dist (Shared И агента) = старый код в проде.
- **Память в SDK-сессии как ЕДИНСТВЕННЫЙ источник** форкает мозг — нужен catch-up из `.db`.
- **Латентность OpenClaw ~100с** — typing обязателен, идти через gateway (тёплый раннер).
- **getUpdates-конфликт** — один процесс на токен (Finn: снять telegram-binding из openclaw.json).
- **A2A handler** должен принимать новый `type`, иначе ответ теряется.
- **Тихий фолбэк на Claude в ORmode** = нарушение развязки.
- **`pgrep`/kill по голому имени** ловит дев-сессии с `.../<Agent>/src` — бить по dist-пути.
- **Telegram parse_mode:'HTML' без `formatForTelegram`** — markdown не рендерится.
- **Процессы не убивать руками** — только через лаунчер ([[feedback_no_kill_process]]).
- **OpenClaw без `--session-key`** валит всё в `agent:<id>:main` (мешает чаты) — давать ключ per-chat.
- **Дрейф СХЕМЫ БД:** `tsc` выкатил новую схему, рассинхронную с живой `.db` → краш `initDatabase`
  (кейс `timestamp`→`created_at`). Чинить **миграцией живой БД под код** (`ALTER TABLE … RENAME/ADD`),
  не откатом кода. (Расширение dist-дрейфа на схему.)
- **Shared-модуль = ТОЛЬКО node-built-ins.** `file:`-симлинк резолвит зависимости из СВОЕГО realpath,
  не из node_modules агента → НЕ может `import 'better-sqlite3'`/third-party. Нужен хэндл — **принимать
  параметром** от вызывающего (передать конструктор `Database`/готовый хэндл). Иначе агент падает на импорте.
- **Чокпоинт «config-only» проверять трассировкой.** Наличие движок-файла ≠ агент им пользуется
  (кейс Freddy: `llm-provider.ts` был, но пайплайн шёл мимо). Перед «переключение = только конфиг» —
  трассировать ФАКТИЧЕСКИЙ `generate()`-путь, что чокпоинт реально подключён. И что ЖИВОЙ вход идёт
  через него (кейс Finn 2026-06-21: `finn-call.ts` exec'ил `openclaw agent` МИМО `generate()` → finn.db-память
  не писалась, личность раздваивалась с OpenClaw-workspace; фикс — гейт зовёт `generate()`, workspace нейтрализован).
- **Транзиент ≠ отказ.** Сетевой блип (`fetch failed`/timeout/5xx/429) НЕ = «API/баланс лёг».
  `withRetry` ~3× с бэкоффом на транзиентные паттерны (auth/4xx НЕ ретраить); не каскадить в
  недоступный фоллбэк; инструкцией запретить агенту выдумывать «API лёг» и откладывать «на потом».
  Различать транзиент/реальное в КОДЕ, не на суждении агента.
- **SDK-builder auth.** Боты ходят через бандл-CLI SDK, auth = подписка (OAuth в Keychain). Разовый
  `401` при рефреше токена = **транзиент** (лечится повтором, каждый ход читает креды заново); назойливо
  → свой `CLAUDE_CODE_OAUTH_TOKEN` (`claude setup-token`). «Blocked by endpoint security» = **косметика
  десктоп-Claude.app**, рантайма ботов НЕ касается ([[endpoint-security-block-desktop-only]]).

**Стиль (человек, не скрипт):**
- Варьируй длину фраз, попадай в энергию/регистр юзера; без штампов («Принято», «Более того») и
  AI-маркер-эмодзи; короткое тире (-), не длинное.
- Короткий вопрос → короткий ответ (1-3 фразы), не перевыполняй простое. Без мета-комментариев о
  своём процессе («думаю», «жду»).
- **Прими решение, дай ОДНО решение, не меню** (ADHD/автономия): лучшее первым, кратко почему.
  (Fallback: если результата точно нет — 2 ближайшие вероятные итерации, не пусто.)
- Следуй буквально — без незапрошенных «улучшений»; не выдумывай задачи; тяжёлый research только по запросу.

**Самообучение и честность:**
- На ЛЮБУЮ коррекцию — сразу В ЭТОМ ЖЕ ходе сформулируй и сохрани урок (`[[SAVE_LESSON]]`), категория
  correction/pattern/insight; не «понял». Ход, потребовавший коррекции = НЕ успех → ищи корень. Урок —
  конкретно/действенно, не «коммуницировать лучше».
- **Не фабрикуй уверенность:** нет в данных → скажи прямо ([[feedback_accuracy_not_assumptions]]); не
  галлюцинируй деталь, которой не видишь.
- Сломалось → проверь СВОЙ вызов (аргументы/текст/порядок) ПЕРЕД кодом; `ok:true` ≠ верный результат.
- **Упорное неверное поведение после переинструктажа = скорее БАГ КОДА, не личность** → смотреть
  реализацию, а не докручивать промпт ([[workflow_agent_communication]]).
- Persistent (Vault/SQLite/git) переживает чистку, volatile (катящийся контекст) — нет: незаписанные
  решения → в persistent ДО любой чистки/новой сессии.

## 15. Vault-структура агента (типовая)

Что у каждого агента есть в Vault (общий граф знаний; рантайм видит файлово):

| Путь | Что | Как работает |
|---|---|---|
| `Vault/rules/<agent>.md` | правила/личность (+ `global.md`, `a2a-protocol.md`) | каноничный человеко-источник правил агента |
| `Vault/lessons/<agent>/` | атомарные уроки `YYYY-MM-DD_тема.md` | пишет агент (`[[SAVE_LESSON]]`→`writeVaultLesson`) и человек; читают оба; weekly-compile → wiki |
| `Vault/reports/<agent>/` | отчёты агента (Jesse `trade-reviews`, Eva/Joe/Freddy/builder/system) | агент кладёт результаты работы |
| `Vault/briefs/{active,completed,archive}/` | межагентные задачи/брифы (`vault-briefs`) | active → в работе; completed/archive — авто-архив отработанных |
| `Vault/wiki/` | граф знаний | уроки компилируются сюда (long-term) |
| `Vault/_config/engines.env` + `<agent>.env` | конфиг движков + секреты | §8 |
| `Vault/architecture/` | спеки + этот Канон | — |
| `Vault/inbox/` | быстрый вход (события/заметки, обработать ≤7д) | агент кладёт, разгребается в wiki/reports |
| `Vault/sessions/` | ИТОГИ сессий (не полные логи) | агент пишет итог по завершении |
| `Vault/processes/` | логи процессов `YYYY-MM-DD_<agent>_тема.md` (a2a, ребилды, запуски) | агент документирует ход работы |
| `Vault/pipeline/` | очередь задач + `watcher` | контентный/задачный конвейер |
| `Vault/drafts/<agent>/` | черновики агента | рабочие наброски до публикации |
| `Vault/dashboard.md` (`Maksim/`) | actionable для владельца | агент ПИШЕТ, владелец читает |

**Агент ↔ Vault = read+write (в т.ч. из Telegram).** Vault — это рабочее пространство агента, не
только источник конфига. Из любого триггера (вкл. сообщение в Telegram) агент **читает** Vault
(`rules`/`wiki`/`lessons` через `buildVaultContext`) И **пишет** в него (`writeVaultLesson`, отчёты в
`reports/`, брифы в `briefs/`, заметки в `inbox/`, actionable в `dashboard.md`) — и берёт результат
обратно позже. Доступ файловый (рантайм видит Vault напрямую; OpenClaw — через свои file/exec-тулы,
SDK — нативно). (Отдельный Obsidian-плагин Telegram-Sync для этого НЕ нужен — он был избыточным
вторым механизмом; запись/чтение делает сам агент своими тулами.)

**Поток инструкций/уроков:** живой промпт = `instructions.ts` (личность в коде) + `buildVaultContext`
(инжект уроков из `Vault/lessons/` через `vault-lessons`) + DB-таблицы. `Vault/rules/<agent>.md` —
каноничный человеко-источник (не всегда инжектится напрямую — при сборке промпта не теряй его смысл).
Коррекция юзера → `[[SAVE_LESSON]]`-маркер → урок в `Vault/lessons/<agent>/` → инжектится в след. промптах.

**Нетиповое (роль агента, НЕ Канон):** напр. **Alice пишет брифы ДРУГИМ агентам** (`briefs/active` для
Joe/Eva — оркестрирует цепочку); Jesse `reports/jesse/trade-reviews` (предметные разборы). Типовое — выше.
(`dreams/`, `Maksim/` — личное/эксперимент владельца, не агентская структура — в Канон не входят.)

## 16. Vault как граф знаний (wiki) — компиляция, навигация, масштаб

Vault = **граф знаний** (Obsidian, `[[wikilinks]]`), не свалка. Принцип «умнее с ростом»: контекст
LLM фиксирован, vault растёт → агент грузит ПРАВИЛЬНЫЕ 5 страниц из 10 000, а не тонет в шуме.

**Без RAG.** Никаких embeddings/vector-search. Агент навигирует по дереву напрямую
(`[[trading/VSA]]`), читает целый файл с backlinks — точно, полный контекст, дёшево.

**Три слоя → компиляция:** сырьё/диалог (своя `<agent>.db`, conversations+FTS, §3) → **weekly
compile** (LLM группирует по темам, синтезирует) → `wiki/<домен>/` (скомпилированные страницы с
`[[wikilinks]]`). **Compile = компрессия** (100 raw → 8-12 wiki, ratio ≥10:1; растёт быстрее →
compile неправильный). `lessons/<agent>/` тоже компилируются в wiki. (Заменяет старый «общий
Archivarius для диалога» — диалог теперь в `<agent>.db`; vault = только скомпилированный ИТОГ.)

**Навигация (масштаб):**
- **`_MOC.md`** — индекс-хаб каждого домена (однострочные описания) → агент читает MOC, грузит
  только нужные страницы (O(1), не O(n)). **`> TL;DR:`** — первая строка каждой страницы → сканировать
  200 TL;DR за контекст. **Query routing:** классифицировать вопрос → домен → `_MOC` → релевантные. НЕ «грузить всё».
- **Agent Lenses:** в `rules/<agent>.md` — `vault_scope` (что читает) + `vault_ignore` (что нет).
  Jesse не грузит контент-план Eva; каждый видит свой срез.

**Качество графа (health-check):** каждая страница ≥2-3 backlinks (orphan = дефект); битые
wikilinks/дубли/stale ловятся аудитом; **pruning:** 60+ дней + 0 backlinks → `archive/`. Можно
выделить агента под health-check/cross-compile — это РЕГУЛЯТОР графа, НЕ единый writer диалога.

**Общие (не пер-агентные) папки:** `wiki/<домен>/` (граф) · `inbox/` (быстрый вход, обработать ≤7д) ·
`sessions/` (ИТОГИ сессий, не логи) · `archive/` (deprecated + старые отчёты) · `_meta/` (contradictions,
health) · `dashboard.md` (агенты пишут actionable, владелец читает). reports lifecycle: 0-6мес
`reports/` → 6мес+ `archive/` → 5лет+ внешний диск (агенты НЕ авто-читают reports, только по запросу).

**Платформа:** Vault — **git-repo** (obsidian-git, авто-коммит ~10мин → версии/откат/мультимашинность
push-pull) + Obsidian-плагины (dataview/templater/folder-notes/shellcommands). Новые файлы — из
шаблонов `Vault/_templates/` (lesson.md, wiki-page.md, inbox-item.md, source-meta.md).

## 17. Анти-галлюцинационный слой (frontmatter + правила) 🔴

Самый нагруженный слой — мешает агенту выдавать догадку за факт и «размножать знание из ничего».
Прямо усиливает [[stale_data_rule]] и §14. (Поля frontmatter уже на живых файлах; правила — здесь.)

**Правила ответа:**
- **«Не знаю».** Нет в vault → явно: «⚠️ нет в базе, это предположение: …». Догадку за факт — никогда.
- **Source citation.** Фактический ответ несёт `[[wikilink]]` на страницу-источник. Нет ссылки = не проверил vault.
- **Verify before act.** Не действовать по памяти прошлой сессии: перечитать страницу, проверить
  `updated:`/`status:`, stale>7д → предупредить (90% галлюцинаций = «помнит» устаревшее).

**Frontmatter wiki/lessons (аудит-трейл):**
- `confidence:` verified | compiled | hypothesis (видит `hypothesis` → оговорка).
- `origin:` external | internal | user. **Anti-circular (закон):** `origin: internal` НИКОГДА не
  становится `external` без человеческой/внешней валидации (иначе A написал → B «подтвердил» → фикция =
  «факт»). Compile флагает internal-страницу, цитируемую как факт, в `_meta/contradictions.md`.
- `grounding:` first-answer | validated · `updated_by:`/`source_session:`/`sources:`. Страницу последним
  менял сам агент → двойная проверка.

**Answer Persistence (консистентность):** дал УНИКАЛЬНЫЙ ответ (web/анализ/мнение) → запиши в wiki
(`confidence: compiled`, `origin: web|internal`, `grounding: first-answer`) + ответь со ссылкой.
Иначе тот же вопрос → каждый раз новый ответ (LLM стохастична); с этим — первый закреплён, дальше
агент читает СВОЙ закреплённый → консистентность; неверно → user correction → lesson → re-compile.

**Порядок загрузки контекста (детерминирован):** `rules/<agent>.md` → `rules/global.md` →
`wiki/<тема>` → сырьё (если wiki не хватает) → `_meta/contradictions.md`. **Contradiction registry:**
при конфликте — оба варианта + статус в `_meta/contradictions.md`; пока не разрешён, агент показывает ОБА.
